# DOM overlay for menu/HUD chrome; Canvas2D stays for the game world

ADR 0001 chose Canvas2D for in-game rendering. That decision didn't cover the surrounding UI — title screen, How To Play, Credits, Pause, Level Complete, All Levels Complete, and the in-game HUD — which Phase 2 needs and which Phase 1 never built. We prototyped both approaches directly rather than reasoning abstractly: a Canvas2D-drawn Pause screen and remaining-lines HUD, and a DOM/CSS equivalent, on [`prototype/ui-approach`](https://github.com/philjhale/rebounder-ts/tree/prototype/ui-approach). DOM won on text layout (no manual line-wrapping/measurement for the ~6 text-heavy menu screens), native click targets (no manual hit-testing), and effort-per-screen.

This decision is scoped to the UI chrome layer only — it doesn't reopen ADR 0001. Canvas2D remains exclusively for in-game world rendering (Balls, Lines, Obstacles, Targets, Teleporters, ColourChangers). The DOM overlay sits positioned on top of the canvas and owns the menu `Screen` state machine, Pause/Level-Complete overlays, and the HUD. Revisit only if a future screen needs frame-accurate animation or effects that DOM/CSS can't express reasonably.
