# ESLint via flat config, typescript-eslint strict-type-checked, no Prettier, lint gated in CI, auto-fixed continuously via a Claude Code hook

ADR 0004 stood up CI with `test`/`typecheck`/`build` as required checks but deliberately excluded lint, since no ESLint config existed yet. This decision closes that gap. We're adding ESLint 9 in flat-config form (`eslint.config.js`, ESM — matching the project's existing `type: module`/bundler setup) with the `typescript-eslint` `strict-type-checked` preset, which layers type-checked rules (`no-floating-promises`, `no-unsafe-*`, etc.) on top of `recommended` and matches the bar the project's `tsconfig.json` already sets with `strict`, `noUnusedLocals`, and `noUnusedParameters`. No Prettier: this decision is scoped to linting, not formatting, and picking a formatter is deferred as its own decision, same way ADR 0004 deferred lint itself.

`lint` becomes a fourth required status check in the existing GitHub Actions workflow, alongside `test`/`typecheck`/`build` — the whole reason ADR 0004 flagged this as a follow-up was to avoid a lint config that ships unenforced and rots. Once configured, `eslint --fix` runs once against the existing codebase (five files in `src/`, small enough to clean up directly rather than merging pre-red or muted with disables) so the check starts green.

Enforcement is also continuous, not just CI-gated: a new `PostToolUse` hook (matcher `Edit|Write`) in `.claude/settings.json` runs `eslint --fix` against just the file Claude edited, mirroring the existing `PreToolUse`/`block-stale-branch-edit.sh` pattern already in this repo. Scope is the single edited file, not the whole tree — CI's `lint` job already covers the full tree per PR, and whole-tree linting on every edit would be wasteful. If `eslint --fix` leaves violations it can't auto-fix, the hook exits non-zero with the error output surfaced back to Claude, so problems get fixed while Claude still has context on the code it just wrote, rather than being deferred to a later CI failure.
